<!--
If managing Python projects ever looked confusing to you, that is because it was. For a long time Python had no single answer to four questions: which Python version, which packages, where do they live, and how do I get exactly the same set again. pip installs packages and stops there. virtualenv, and later venv in the standard library, gave each project its own folder of packages. conda came from the scientific world and installs Python and compiled libraries too, but in its own channels, apart from the rest. pipenv and Poetry each tried to combine the pieces and add a lockfile, and Hatch, PDM and Rye followed with their own take. Out of all that came one thing everybody now shares: the pyproject.toml file as the description of a project. uv, from 2024, reads that file and covers all four questions in one program, which is why we use it. The reason to show this history is practical: older tutorials, existing projects at work and Copilot will hand you pip install, conda activate or poetry add. You should recognise them as older answers to the same job, and know the uv command that does it.

<!--
This is the why behind the folder called .venv that you have seen since this morning. Start with the problem on the left. If every project uses the one set of packages that belongs to the Python on your laptop, there is room for one version of each package. You wrote bench-report last year against numpy 1.26. Today you start vibration-analysis, which needs numpy 2.5, so you install it. That replaces 1.26, and the next time you run bench-report it fails, although you did not touch it. MATLAB users know this as two projects that need different toolbox versions on one installation. The right side is the answer: a virtual environment is a private set of packages for one project, stored in a folder called .venv inside the project folder. Each project has its own, so installing for one cannot change another. It also fixes the Python version per project. It costs disk space and nothing else. The note is the second thing to remember: the .venv is a result, not a source. The project file says what should be in it, uv builds it, and you can delete it at any time and build it again with uv sync. That is why it stays out of Git, and why you never copy a .venv to a colleague: they get the project file and the lockfile and build their own. The next slides show the project file and the lockfile.
-->

# Two commands give a project <span class="dm-accent">its own packages</span>

```powershell
uv init --no-package bench-tools
cd bench-tools
uv add matplotlib
uv run python main.py
```

```text
Creating virtual environment at: .venv
Resolved 12 packages in 330ms
Installed 11 packages in 68ms
 + matplotlib==3.11.2
 + numpy==2.5.4
 ...
```

<p class="note">numpy came along without you asking, because matplotlib needs it: a <b>transitive dependency</b>.</p>

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }
</style>

<!--
uv init creates a folder with pyproject.toml, a starter main.py, a .python-version file and a .gitignore. The --no-package flag asks for a plain script project: without it, recent uv versions make an installable package with a src folder and no main.py. uv add finds a compatible set of versions, creates the project's own .venv if needed, installs, and records the choice. Matplotlib brought ten packages with it, only the first lines are shown, and your versions will differ. Notice that there is no activation step: uv run makes sure the .venv matches the project and runs the command inside it. In VS Code, choose the .venv interpreter once and the play button does the same. To remove a package, run uv remove followed by the name.
-->

# One script, no project: <span class="dm-accent">the packages go in the file</span>

<div class="split">
<div>

```python
# /// script
# requires-python = ">=3.13"
# dependencies = [
#     "matplotlib>=3.11.2",
# ]
# ///
import matplotlib.pyplot as plt

plt.plot([7.1, 7.4, 7.6])
plt.savefig("pressure.png")
```

</div>
<div>

```powershell
uv add --script plot.py matplotlib
uv run plot.py
```

- The comment block at the top is **inline script metadata**, a Python standard (PEP 723)
- `uv add --script` writes it for you
- `uv run` reads it, builds a temporary environment and runs the script

</div>
</div>

<p class="note">One file to mail to a colleague: use this. Several files, tests or a lockfile: make a project.</p>

<style>
.slidev-code { font-size: 15px !important; line-height: 1.45 !important; }
</style>

<!--
A project folder with pyproject.toml is the right form once a tool grows. For a single script it is a lot of ceremony. Since 2024 Python has a standard for this, PEP 723: the script itself says which Python and which packages it needs, in a comment block at the top. Python ignores the block, because it is a comment. Tools read it. uv add with the script flag writes or updates the block, and uv run on the file reads it, creates a throwaway environment with exactly those packages, and runs the script. Nothing is installed into a project, and there is no .venv folder next to the file. The practical use: you write a small analysis script and send the one file to a colleague. They type uv run and the name, and it works, with the same packages. The tradeoff: there is no lockfile by default, so the exact versions can differ over time, and it does not scale to several files or to tests. That is when you move to a project.
-->
