<!--
If managing Python projects ever looked confusing to you, that is because it was. For a long time Python had no single answer to four questions: which Python version, which packages, where do they live, and how do I get exactly the same set again. pip installs packages and stops there. virtualenv, and later venv in the standard library, gave each project its own folder of packages. conda came from the scientific world and installs Python and compiled libraries too, but in its own channels, apart from the rest. pipenv and Poetry each tried to combine the pieces and add a lock file, and Hatch, PDM and Rye followed with their own take. Out of all that came one thing everybody now shares: the pyproject.toml file as the description of a project. uv, from 2024, reads that file and covers all four questions in one program, which is why we use it. The reason to show this history is practical: older tutorials, existing projects at work and Copilot will hand you pip install, conda activate or poetry add. You should recognise them as older answers to the same job, and know the uv command that does it.
-->

<!--

Start with why: each project gets its own virtual environment, a folder called .venv with its own packages, so installing something for one project cannot break another. Without it, two projects that need different versions of the same package collide, like different toolbox versions on one MATLAB installation. pip only installs packages, so you manage the environment, the activation and the requirements file yourself. uv covers Python versions, environments, installation and locking in one tool, and it is much faster. You will meet pip in older tutorials, so it helps to know the mapping. # Two commands give a project <span class="dm-accent">its own packages</span>

```powershell
uv init bench-tools
cd bench-tools
uv add matplotlib
uv run python main.py
```

```text
Creating virtual environment at: .venv
Resolved 12 packages in 330ms
Installed 11 packages in 68ms
 + matplotlib==3.11.2
 + numpy==2.5.4
 ...
```

<p class="note">numpy came along without you asking, because matplotlib needs it: a <b>transitive dependency</b>.</p>

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }
</style>

<!--
uv init creates a folder with pyproject.toml, a starter main.py, a .python-version file and a .gitignore. uv add finds a compatible set of versions, creates the project's own .venv if needed, installs, and records the choice. Matplotlib brought ten packages with it, only the first lines are shown, and your versions will differ. Notice that there is no activation step: uv run makes sure the .venv matches the project and runs the command inside it. In VS Code, choose the .venv interpreter once and the play button does the same. To remove a package, run uv remove followed by the name.
-->

# <span class="dm-accent">pyproject.toml</span> declares, <span class="dm-accent">uv.lock</span> pins

```toml
[project]
name = "bench-tools"
requires-python = ">=3.13"
dependencies = [
    "matplotlib>=3.11.2",
]
```

# One script, no project: <span class="dm-accent">the packages go in the file</span>

<div class="split">
<div>

```python
# /// script
# requires-python = ">=3.13"
# dependencies = [
#     "matplotlib>=3.11.2",
# ]
# ///
import matplotlib.pyplot as plt

plt.plot([7.1, 7.4, 7.6])
plt.savefig("pressure.png")
```

</div>
<div>

```powershell
uv add --script plot.py matplotlib
uv run plot.py
```

- The comment block at the top is **inline script metadata**, a Python standard (PEP 723)
- `uv add --script` writes it for you
- `uv run` reads it, builds a temporary environment and runs the script

</div>
</div>

<p class="note">One file to mail to a colleague: use this. Several files, tests or a lock file: make a project.</p>

<style>
.slidev-code { font-size: 15px !important; line-height: 1.45 !important; }
</style>

<!--
A project folder with pyproject.toml is the right form once a tool grows. For a single script it is a lot of ceremony. Since 2024 Python has a standard for this, PEP 723: the script itself says which Python and which packages it needs, in a comment block at the top. Python ignores the block, because it is a comment. Tools read it. uv add with the script flag writes or updates the block, and uv run on the file reads it, creates a throwaway environment with exactly those packages, and runs the script. Nothing is installed into a project, and there is no .venv folder next to the file. The practical use: you write a small analysis script and send the one file to a colleague. They type uv run and the name, and it works, with the same packages. The tradeoff: there is no lock file by default, so the exact versions can differ over time, and it does not scale to several files or to tests. That is when you move to a project.
-->
