# One <span class="dm-accent">environment</span> per project

<DmColumns class="mt-4">
<DmColumn header="Shared installation" tone="plain">

- Project A needs a package at version 1
- Project B needs version 2
- Only one can be installed, one project breaks

</DmColumn>
<DmColumn header="Virtual environment per project" tone="violet">

- Each project has its own folder <code>.venv</code>
- It holds its own Python link and its own packages
- Projects cannot disturb each other

</DmColumn>
</DmColumns>

<!--
Think of a virtual environment as a private toolbox per project. Without it, installing a package for one project changes what another project sees. This is the same problem as different MATLAB toolbox versions on one machine, solved by giving each project its own copy. The folder is created by uv, you never edit its contents.
-->

<!--
pip is the classic tool and still works, but it only installs packages. You manage the environment, the activation and the requirements file yourself. uv covers Python versions, environments, installation and locking in one tool, and it is much faster. On a managed laptop that matters, because it also installs Python without admin rights. You will meet pip in older tutorials, so it helps to know the mapping.
-->

# Start a project: <span class="dm-accent">uv init</span>

```powershell
uv init bench-tools
cd bench-tools
```

```text {all|2|3|4|5|6|all}
bench-tools/
  .python-version    Python version for this project
  README.md          describe the project
  main.py            starter script
  pyproject.toml     project settings and dependencies
  .gitignore         files Git should skip
```

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }
</style>

<!--
uv init creates a folder with a minimal project. The .python-version file says which Python to use, pyproject.toml is the heart of the project, main.py is a starter script. Depending on where you run it, uv may also initialise a Git repository, which is why you see a .git folder there as well. After the first uv add or uv run, a .venv folder and a uv.lock file appear.
-->

# <span class="dm-accent">pyproject.toml</span> declares what you need

```toml {all|2|4|5|6-8|all}
[project]
name = "bench-tools"
version = "0.1.0"
requires-python = ">=3.13"
dependencies = [
    "rich>=15.0.0",
]
```

<v-click>

<p class="mt-2">Human readable, and edited for you by <code>uv add</code> and <code>uv remove</code>.</p>

</v-click>

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }
</style>

<!--
This file lists the name, the Python version and the packages the project needs, with minimum versions. It is a statement of intent: "I need rich, at least version 15". TOML is just a simple settings format, sections in square brackets and key equals value. You can edit it by hand, but normally uv does it for you.
-->

# Add a package with <span class="dm-accent">uv add</span>

<v-click>

<p class="mt-2">One command: creates <code>.venv</code> if needed, installs, updates <code>pyproject.toml</code> and <code>uv.lock</code>.</p>

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }

# <span class="dm-accent">uv.lock</span> pins exact versions

```toml {all|1-4|6|all}
[[package]]
name = "rich"
version = "15.0.0"
source = { registry = "https://pypi.org/simple" }
...
```

<DmColumns class="mt-4">
<DmColumn header="pyproject.toml" tone="navy">

Says what you need: <code>rich>=15.0.0</code>

</DmColumn>
<DmColumn header="uv.lock" tone="violet">

Records what you got: <code>rich 15.0.0</code>, plus every dependency and file hash

</DmColumn>
</DmColumns>

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }
</style>

<!--
The lock file is written by uv and never edited by hand. It fixes the exact version of every package, including the ones you did not ask for. That is what makes your colleague's environment, and the build server on day 3, identical to yours. Commit it to Git. Run uv lock to refresh it without installing anything.
-->

# No activation: <span class="dm-accent">uv run</span> does it

```python
# main.py
from rich.console import Console

console = Console()
console.print("Run TB-014: [bold green]OK[/]")
```

```powershell
uv run python main.py
```

```text
Run TB-014: OK
```

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }
</style>

<!--
With pip you activate the environment first and forget it half the time. With uv you simply put uv run in front. It makes sure the .venv exists, matches the lock file, and runs the command inside it. In the terminal the word OK shows in green. In VS Code, choose the .venv interpreter once and the play button does the same.
-->

# What goes into <span class="dm-accent">Git</span>, and what does not

<DmColumns class="mt-4">
<DmColumn header="Commit" tone="violet">

- `pyproject.toml`
- `uv.lock`
- `.python-version`
- your `.py` files and `README.md`

</DmColumn>
<DmColumn header="Do not commit" tone="plain">

- `.venv/`, big and machine specific
- `__pycache__/`, generated

</DmColumn>
</DmColumns>

```powershell
uv sync
```

<p class="mt-2">A colleague clones the repository, runs <code>uv sync</code>, and gets your environment.</p>

<style>
.slidev-code { font-size: 17px !important; line-height: 1.5 !important; }
</style>

<!--
The rule: commit the recipe, not the result. The lock file plus pyproject.toml are the recipe, and uv sync rebuilds .venv from them on any machine. The .gitignore generated by uv already excludes .venv. This is the link to the afternoon: Git is where these files are shared.
-->
